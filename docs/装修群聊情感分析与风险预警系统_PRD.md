## 1. 项目概述

### 1.1 项目背景

装修行业是消费投诉高发领域。业主与装修公司的沟通主阵地是企业微信业主群，大量不满情绪（增项、停工、偷工减料等）首先在群聊中发酵。项目经理通常同时负责十余个群，靠人工翻群消息发现风险，存在三个痛点：

1. **发现晚**：等负面情绪升级到拨打 12315、上门维权时才察觉，错过最佳安抚窗口；
2. **看不全**：一人盯十几群、每天上千条消息，负面消息极易被刷过；
3. **判不准**：业主负面情绪大量以反讽、阴阳怪气、碎片化短消息形式出现（如"这墙裂得跟蜘蛛网似的，真棒👍"），关键词告警基本失效。

### 1.2 项目目标

构建一套基于 **BERT 架构模型微调** 的中文群聊情感分析与风险预警系统：

* 输入装修业主群聊消息流，自动输出 **情感标签（正/中/负）+ 风险类别（7 类装修风险/无风险/其他风险）+ 风险等级（低/中/高）**；
* 高风险消息经 **n8n 工作流** 立即推送至实际负责处理的项目经理；中、低风险消息保留在数据库中，不主动打扰项目经理；
* 全量分析结果落库（MySQL），支持按项目、风险类别、风险等级和时间范围查询与复盘。

### 1.3 业务价值

* 投诉风险发现时间从「事后被动处理」提前至「群内情绪出现即感知」；
* 项目经理从「人肉盯群」解放为「只看系统推送的高危消息」，单人均可管理群数量成倍提升；
* 风险判断可追溯，能够查看情感、风险类别、风险等级及对应模型概率，便于复盘模型为何作出该判断。

## 2. 用户与使用场景

| 角色         | 诉求                      | 与系统的交互                        |
| ---------- | ----------------------- | ----------------------------- |
| 项目经理（核心用户） | 第一时间获知哪个群、哪位业主情绪高危，提前介入 | 接收企微群告警；按需查询数据库中的分析记录并跟进风险 |
| 客服/运营主管    | 掌握各项目群整体舆情，周报复盘         | 查询数据库中的风险记录与分级统计            |
| 算法工程师（开发者） | 数据标注、模型训练和参数调优          | 管理数据集版本，完成训练、评估和模型发布            |

**典型场景**：业主在 3 栋业主群连发 4 条短消息："钱交了三个月了""就挂了个网""再不给说法""我打 12315"。系统在该群连续 2 分钟无新消息时结束当前对话段；如对话持续进行，则在当前段达到 300 tokens 或持续 5 分钟时强制结束。模型结合最近两个对话段的上下文，对当前段判定情感为负面、风险类别为「工期拖延」、风险等级为高 → n8n 推送告警至实际负责处理的项目经理 → 项目经理当日介入。原始消息、上下文关系及模型三项输出写入 MySQL，供后续查询与复盘。

## 3. 技术选型论证

### 3.1 技术路线：预训练模型微调

本项目采用「预训练 + 微调」路线：直接在大规模中文语料上预训练好的模型基础上，使用现有装修领域标注数据进行微调。相比从零训练，该路线自带中文语言知识，所需训练资源更少，并可在消费级 GPU 上完成训练。

### 3.2 任务性质决定模型类型：为什么是 Encoder 模型

本任务为**文本理解类任务**（分类/打分），而非生成类任务。Transformer 模型分三种形态：

| 类型               | 结构             | 代表模型         | 适用任务                 |
| ---------------- | -------------- | ------------ | -------------------- |
| **Encoder-only** | 仅编码器，**双向注意力** | BERT、RoBERTa | **理解类**：分类、情感分析、实体识别 |
| Decoder-only     | 仅解码器，单向注意力     | GPT 系列、Qwen  | 生成类：对话、写作            |
| Encoder-Decoder  | 两者皆有           | T5、BART      | 转换类：翻译、摘要            |

关键差异在注意力机制：

* **Encoder（双向注意力）**：每个词能同时看到整句话的所有词。例："这墙裂得跟蜘蛛网似的，真棒👍"中，"真棒"能看到前文的"裂"，模型才能识别这是反讽；
* **Decoder（单向/因果注意力）**：每个词只能看到它左边的词，天生为逐字生成设计，不为通读判断设计。

情感分类需要**通读全句再下判断**，与 Encoder 架构天然匹配。补充两点排除说明：

* **不用 T5 等 Encoder-Decoder 模型**：该类模型为翻译、摘要等生成任务设计，其 Decoder 部分对纯分类任务是无效负担（参数量翻倍），且标签需以文本形式生成再解析，稳定性不如分类头直接输出概率；
* **不用 Decoder-only 大模型**：见 3.5 对比。

故选型范围锁定 Encoder-only 的 BERT 架构模型。

### 3.3 BERT 的工作方式与微调原理

**"BERT"一词包含三层含义**，需区分：

1. **架构**：12 层 Transformer 编码器（768 维隐藏层、12 注意力头，base 版约 1.1 亿参数）；
2. **预训练方法**：掩码语言模型（MLM）——随机遮住输入中 15% 的词让模型猜，逼迫模型理解上下文；
3. **具体预训练权重**：可下载直接加载的模型文件。

**用 BERT 做分类的原理**：输入文本前加一个特殊标记 `[CLS]`，经过 12 层编码后，`[CLS]` 位置的输出向量被设计为"整句话的语义浓缩"，在该向量后接一个简单的全连接分类层（分类头），输出各类别概率：

```
"再不给说法我打12315"
  → 分词 → [CLS] 再 不 给 说 法 我 打 12315
  → 12层 Transformer 编码（双向注意力）
  → 取 [CLS] 向量（768维）
  → 分类头（全连接层 + softmax）
  → 负面 0.97 / 中性 0.02 / 正面 0.01
```

**微调（Fine-tuning）**：预训练权重已经具备中文语义能力，项目使用装修领域标注数据继续训练，让模型学习装修群聊中的情感、风险类别和风险等级边界。实际训练轮数由验证集表现和早停结果确定，不提前写死。

### 3.4 基座模型选型：chinese-roberta-wwm-ext

候选基座对比：

| 对比项 | bert-base-chinese（谷歌原版） | chinese-roberta-wwm-ext（本项目选择） |
| --- | --- | --- |
| 模型规模 | BERT-base：12 层、隐藏维度 768、12 个注意力头 | BERT-base 规格，约 1.02 亿参数 |
| 发布方 | Google | 哈工大讯飞联合实验室（HFL） |
| 预训练数据 | 中文维基百科，约 0.4B tokens | 中文维基百科及扩展中文语料，约 5.4B tokens |
| 遮盖方式 | WordPiece 级遮盖 | 全词遮盖 WWM |
| 训练设置 | 包含 NSP 任务 | 不使用 NSP；官方说明未使用动态遮盖 |
| 加载方式 | `BertTokenizer` + `BertModel` | `BertTokenizer` + `BertModel` |
| 下游效果 | 作为基础对照 | 不同任务表现不同，是否适合本项目由同数据、同配置实验验证 |

**为什么选择全词遮盖（WWM）**：中文词语经 WordPiece 分词后可能由多个字组成。WWM 在预训练时对同一词对应的多个 token 一起执行遮盖，使模型更关注完整词语及其上下文。对于“增项”“挂网”“空鼓”等装修领域表达，这一预训练方式具有合理的适配基础，但最终效果仍以本项目数据上的实验结果为准。

**结论**：`hfl/chinese-roberta-wwm-ext` 保持 BERT-base 规格，可使用 Hugging Face 的 BERT 加载与分类微调流程；其扩展中文预训练语料和 WWM 设置与装修群聊文本具有较好的任务匹配度，因此作为本项目首选基座，`bert-base-chinese` 作为对照备选。最终选型结论由本项目的锁定测试集结果验证。

### 3.5 基准与对比方案

项目使用同一份锁定测试集比较三种方案：

| 方案 | 实现方式 | 定位 |
| --- | --- | --- |
| 未微调 Encoder 基准 | 冻结预训练 `chinese-roberta-wwm-ext` Encoder，仅训练三个分类头 | 检查原始预训练特征在当前任务上的基础表现 |
| LLM Zero-shot | 使用固定提示词和固定结构化输出格式，不提供训练示例 | 作为通用大模型能力参考 |
| 微调模型 | 使用装修领域标注数据训练 Encoder 和三个分类头 | 项目最终模型 |

三种方案均按最终高风险告警结果计算告警误报比例，并同时记录告警数量、漏掉的高风险数量和推理耗时。项目不预设哪种方案一定更优，以实际测试结果作为模型选型依据。

### 3.6 选型结论

* **路线**：预训练 + 微调（数据门槛与本项目匹配）；
* **模型形态**：Encoder-only（双向注意力，理解类任务最优）；
* **基座**：`hfl/chinese-roberta-wwm-ext`（WWM + 扩展中文预训练语料，本项目首选基座）；
* **验证**：项目内对比未微调 Encoder 基准、LLM Zero-shot 与微调模型，并执行推理性能测试。

## 4. 需求描述

系统按完整业务与模型工程流程组织：

```text
数据集采集 → 数据标注 → 模型训练 → 模型评估
     → 消息预处理 → 模型推理 → 风险等级判断
     → 结果存储与查询 → 高风险告警 → 月度复盘
```

### 4.1 数据集采集

系统训练数据采用装修领域模拟群聊数据。数据按照业务侧已整理的结构化文字消息格式生成，用于完成数据清洗、对话聚合、人工标注、数据集划分和模型训练。

| 数据类型 | 数据来源 | 主要用途 |
| --- | --- | --- |
| 装修领域数据 | 按项目原始消息字段模拟生成并人工标注 | 学习装修行业表达、多人上下文、风险类别和反讽等难例 |

数据采集要求如下：

1. 每条数据记录生成批次、文本内容和处理状态；模拟数据不得伪装成真实业务数据。
2. 模拟数据应覆盖七类装修风险，同时加入正面、中性、普通咨询和无法归类的负面表达，避免数据只包含投诉样本。
3. 重点覆盖群聊中的短句拆分、口语、省略、错别字、表情、反讽、连续追问和无情绪词的负面事实陈述。
4. 模拟数据使用虚构姓名和项目信息，不生成手机号、详细地址、身份证号、合同编号等个人敏感信息。
5. 模拟原始消息仅包含文本，字段固定为 `message_id、group_name、sender_id、sender_name、sender_role、sent_at、content`；同一群的群名保持固定，用于关联装修项目。
6. 原始数据只追加不覆盖；清洗、聚合和标注结果单独保存，并通过 `dataset_version` 记录数据集版本。
7. 现有数据完成聚合和标注后统一纳入版本化数据集，再按既定比例划分训练集、验证集和测试集；项目同时保留部分样本用于展示从原始消息到人工标注数据的完整流程。

### 4.2 数据标注

#### 4.2.1 标签体系

每个装修领域标注样本由“最多两个历史对话段 + 当前对话段”组成，并包含三层标签。历史对话段只提供语义上下文，三项标签均针对当前对话段结合上下文后的业务含义：

1. **情感标签**：正面、中性、负面。
2. **风险类别标签**：
   * 七类装修风险：恶意增项、工期拖延、偷工减料、材料以次充好、合同陷阱、售后失联/推诿、定金/停工威胁；
   * `无风险`：正面、中性、普通咨询或与装修风险无关的内容；
   * `其他风险`：存在负面风险，但无法稳定归入七类装修风险的内容。
3. **风险等级标签**：低、中、高，表示消息对项目经理介入时效的要求。

风险类别现阶段采用单标签标注。一条消息涉及多个问题时，选择业务风险最高的类别作为主类别，并在备注中记录其他候选类别；多风险样本充足后再升级为多标签任务。

#### 4.2.2 标注规则

* 反讽、阴阳怪气按真实语义标注，例如“这墙裂得真漂亮”标为负面；
* 纯咨询标为中性，风险类别标为`无风险`；
* 没有明显情绪词但描述延期、开裂、失联等事实时，仍标为负面及对应风险类别；
* 风险等级按是否需要项目经理介入及介入时效标注，不按单个关键词或情绪激烈程度直接决定；
* 正面和中性样本的风险类别统一标为`无风险`、风险等级统一标为低；与装修业务风险无关的负面表达也标为`无风险`和低风险；高风险样本的风险类别不得标为`无风险`；
* 信息不足、类别存在歧义的样本标记为待确认，不进入当前训练集。

#### 4.2.3 标注检查

1. 使用 Excel 完成装修领域数据标注，填写情感、风险类别、风险等级和必要备注。
2. 标注前统一标签定义和示例；存在歧义的样本标记为待确认，不强行加入训练集。
3. 标注完成后检查字段完整性、重复样本和类别分布，发现口径不一致时先修正标注规则再继续标注。
4. 每条标注保留标注状态、标注时间、标签版本和备注，保证标签可追溯。
5. 训练样本在 MySQL 中完成清洗、聚合和标注管理；每次训练前按 `dataset_version` 查询已完成标注的样本，导出固定 CSV/JSONL 快照后再训练，禁止直接对持续变化的在线查询结果训练。

### 4.3 模型训练

1. 基座模型采用 `chinese-roberta-wwm-ext`，备选模型为 `bert-base-chinese`。
2. 模型使用共享 Encoder，并通过三个分类头完成三项任务：
   * 情感分类输出正面、中性、负面三类概率；
   * 风险类别分类输出七类装修风险、`无风险`和`其他风险`共九类概率。
   * 风险等级分类输出低、中、高三类概率。
3. 基准模型冻结预训练 Encoder，仅使用训练集训练三个分类头；微调模型使用相同数据划分，同时训练 Encoder 和三个分类头。
4. 数据按训练集 70%、验证集 15%、测试集 15% 划分；同一会话或同一批高度相似样本不得跨集合，避免数据泄漏。
5. 划分时对情感和风险类别进行分层抽样；测试集锁定，不参与调参。
6. 训练过程记录超参数、随机种子、数据集版本、基座模型版本、训练日志和模型权重，生成唯一 `model_version`。
7. 使用验证集监控损失和核心指标，并通过早停、类别权重或采样策略缓解过拟合与类别不平衡。
8. `chinese-roberta-wwm-ext` 最大输入长度为 512 tokens。当前对话段最多 300 tokens，按时间顺序向前取最近两个对话段补充上下文，序列化后的完整输入最多 450 tokens；不足 450 tokens 时保持实际长度，不人工填充内容。超长时优先删除最早上下文，始终优先保留当前对话段。

### 4.4 模型评估、对比与性能测试

#### 4.4.1 告警效果评估

1. 核心评测指标为**告警误报比例**：`错误高风险告警数 ÷ 全部高风险告警数`，等于 `1 - 高风险 Precision`。只有模型最终判定为高风险并进入告警链路的样本计入分母。
2. 第一版验收要求告警正确率不低于 85%，即告警误报比例不高于 15%；项目目标为告警正确率达到 95% 以上，即告警误报比例控制在 5% 以内。评估报告同时记录测试集实际高风险数量、模型高风险告警数量和漏掉的高风险数量；未产生任何高风险告警时，误报比例记为不可计算，不视为通过。
3. 锁定测试集不参与早停、模型选择或提示词修改，只在最终模型和配置确定后评估一次。
4. 未微调 Encoder 基准、LLM Zero-shot 和微调模型使用同一锁定测试集。LLM 使用固定提示词、模型版本和推理参数；三种方案统一按最终高风险告警结果计算误报比例。
5. 情感、风险类别和风险等级的混淆矩阵及典型错误样本作为误判分析材料，不作为当前业务验收的核心指标。
6. 自动生成评估报告，包含各方案的告警数量、错误告警数量、告警误报比例、漏掉的高风险数量、混淆矩阵和典型误判样本。

#### 4.4.2 推理性能测试

1. 性能测试使用最终微调模型和固定的最长 450 tokens 输入，在 NVIDIA GeForce RTX 3080 10GB 环境下执行；推理精度统一设为 BF16，并记录 CUDA、PyTorch、Transformers、驱动版本、模型版本和测试参数。测试结果仅代表 RTX 3080 10GB 环境，不直接外推为其他硬件的处理能力。
2. 从批大小 `1、8、16、32、64` 逐级增加；仍能稳定运行时继续扩大，直到出现显存或内存不足或推理错误。
3. 每个批大小重复回放固定性能测试数据并连续运行至少 5 分钟，记录平均延迟、P95 延迟、每秒处理对话段数、峰值内存或显存占用和错误数量。
4. 将无推理错误、无内存溢出且可连续稳定完成测试的最高批大小记为最大稳定批大小；同时在所有稳定配置中选择实测吞吐量最高的批大小作为推荐批大小，并以对应吞吐量表示当前硬件的模型推理能力。
5. 性能报告不预设吞吐量结论，以实测数据说明模型在当前硬件上每秒和每分钟最多可稳定处理多少个对话段。

### 4.5 消息接入与预处理

1. 系统读取业务侧提供的 CSV 格式结构化文字消息数据。
2. 原始输入字段固定为：`message_id、group_name、sender_id、sender_name、sender_role、sent_at、content`；使用 `message_id` 去重，避免重复分析和重复告警。
3. 当前版本仅接收文本消息，不设计图片、语音、文件或链接的处理流程。业主、项目经理、设计师、工长、工人和客服等角色的消息均保留，用于还原多人群聊上下文。
4. 不按固定分钟窗口机械切分。系统为每个群维护独立消息缓冲区，新消息按时间顺序持续追加；连续 2 分钟无新消息时，认为当前对话段自然结束并送入模型。
5. 为避免活跃群一直无法结束，当前对话段达到 300 tokens 或从首条消息开始持续 5 分钟时强制结束，满足任一条件即可送入模型。
6. 每个当前对话段最多向前读取最近两个已结束对话段作为上下文，最终输入不超过 450 tokens。上下文只辅助判断当前段，不重复生成标签或告警。
7. 文本清洗仅统一异常空白和不可见字符，保留否定词、重复标点、表情、错别字和口语表达；原始 `content` 不得被清洗结果覆盖。
8. 对话段仅在代码运行过程中维护，不单独建表；分析结果保留原始 `message_id` 列表、上下文消息 ID、群名、起止时间和结束原因，保证预测结果可追溯。

### 4.6 模型推理

1. 系统加载指定 `model_version`，将“最近两个历史对话段 + 当前对话段”序列化后执行批量推理，默认批大小为 32，批大小可配置。
2. 每条分析结果输出：
   * 情感标签及正面、中性、负面三类概率；
   * 主风险类别及九类风险概率；
   * 风险等级及低、中、高三类概率；
   * 候选风险类别；
   * 原始消息 ID 列表、推理时间和模型版本。
3. 情感、风险类别和风险等级均由模型根据完整文本语义判断，当前版本不使用关键词加权或人工配置分数参与模型结果计算。
4. 单条消息涉及多个风险时，输出业务影响最高的类别作为主类别，同时保存其他候选类别及概率供后续复盘。
5. 推理失败的记录进入失败清单，不得影响同批次其他消息继续处理。

### 4.7 风险等级与告警决策

1. 风险等级由模型第三个分类头直接输出低、中、高三类概率及最终等级，不再计算 0～100 紧急度分。
2. 低风险表示正常沟通、咨询或无需项目经理介入；中风险表示存在明确问题，需要后续关注；高风险表示需要项目经理及时介入。
3. 当前版本不启用运行时关键词兜底。关键词和典型短语只用于检查训练数据与测试数据的场景覆盖，不参与线上加分或强制改级。
4. 风险等级最终预测结果为高时直接进入即时告警链路，不再额外设置高风险概率阈值。
5. 所有低、中、高风险结果均写入数据库；只有达到高风险告警条件的结果才即时推送项目经理。
6. 当前策略为“少推送、不少记录”：风险识别结果完整保留，高风险即时告警优先保证精确率，避免频繁误报导致项目经理忽略告警。
7. 配置文件仅管理模型版本、批大小、静默结束时长、当前段 token 阈值、最长持续时长、上下文段数、最大输入 token、n8n Webhook 和输出位置等系统参数。

### 4.9 风险告警

1. 达到高风险告警条件的结果通过 HTTP POST 发送至 n8n Webhook，由 n8n 完成告警文案格式化、失败重试和企微群机器人推送。
2. 系统根据当前群对应的项目经理姓名查询项目经理映射表，取得企微告警接收目标后交给 n8n 完成推送。
3. 告警内容至少包含：群名、参与业主、消息摘要、主风险类别、风险等级、高风险概率和消息时间。
4. 中、低风险结果不即时推送，只写入 MySQL，避免用低优先级信息频繁打扰实际负责处理的项目经理。
5. 同一分析单元只发送一次高风险告警，防止任务重跑造成重复推送。
6. 系统记录告警发送时间、发送结果、失败原因和重试次数，便于检查告警链路是否正常。

### 4.10 月度复盘

本节属于系统交付后的持续维护规划，不纳入当前版本的开发、验收和交付范围。

1. 每月复盘全部高风险告警，并抽样检查中、低风险结果，重点发现高风险误报和漏报。
2. 月度复盘统计高风险告警数量、错误告警数量、告警误报比例、中低风险抽样中的高风险漏报数、各类别分布和典型错误样本。
3. 复盘结果形成独立报告，用于说明模型当前表现和主要误判类型，不纳入首次项目验收。

## 5. 整体技术架构

```
【输入数据】业务侧提供的结构化文字消息 CSV
   ↓
【原始输入】文本明文 CSV：消息ID、固定群名、发送人、角色、时间、正文
   ↓
【上下文构建】按群缓冲 → 静默2分钟/300 tokens/持续5分钟结束当前段 → 回看最近2段 → 总长≤450 tokens
   ↓
【模型】RoBERTa-wwm 微调 → 情感 + 风险类别 + 风险等级
   ↓
【告警决策】风险等级为高 → 即时推送
   ↓
【输出】MySQL 原始消息表 + 分析结果表
   ↓
【告警】高风险 → n8n → 企微群机器人推送实际项目经理
   ↓
【后续维护】月度复盘 → 形成模型表现与典型误判报告（不纳入当前交付）
```

## 6. 验收标准

验收使用固定测试数据和固定配置执行。模型指标门槛应在基线实验完成后、正式调优前确定并冻结，不得根据最终测试结果反向修改。

| # | 验收项 | 通过标准 |
| --- | --- | --- |
| 1 | 数据集采集 | 模拟装修群聊数据可追溯生成批次；数据完成去重和清洗；原始数据与处理后数据分开保存，并生成明确的数据集版本 |
| 2 | 数据标注与划分 | 情感、风险类别和风险等级字段完整；待确认样本未进入训练集；训练集、验证集、测试集比例正确，且同一会话或高度相似样本不存在跨集合泄漏 |
| 3 | 模型训练可复现 | 使用指定数据集版本、配置和随机种子能够重新完成训练；模型权重、训练日志、超参数和 `model_version` 保存完整 |
| 4 | 模型评估 | 使用锁定测试集计算告警误报比例；第一版告警正确率不低于 85%（误报比例不高于 15%），项目目标为 95% 以上（误报比例不高于 5%）；评估报告同时记录实际高风险数量、模型告警数量、错误告警数量和漏掉的高风险数量；零告警结果不得按零误报通过 |
| 5 | 对比实验 | 未微调 Encoder 基准、LLM Zero-shot 和微调模型使用同一锁定测试集及统一告警口径；各方案的误报比例、告警数量、漏掉的高风险数量和推理耗时记录完整 |
| 6 | 推理性能 | 在 RTX 3080 10GB、BF16 推理环境下完成批大小递增压测；报告最大稳定批大小、平均与 P95 延迟、每秒处理对话段数、峰值显存占用和错误数量，并明确该环境的最大稳定处理能力 |
| 7 | 分析主链路 | 固定 CSV 测试文件能够依次完成导入、去重、按群缓冲、自然结束或强制分段、最近两个上下文拼接、模型推理和风险等级判断；输入、成功和失败数量能够对账；单条失败不影响同批其他数据 |
| 8 | 风险等级判断 | 预设样本能够稳定输出低、中、高风险及三类概率；当前版本不使用关键词加权、人工配置分数或额外概率阈值；所有风险结果均正确落库，风险等级最终预测为高的结果进入即时告警链路 |
| 9 | 存储与查询 | 原始消息写入 `raw_messages`，模型分析和告警结果写入 `analysis_results`；对话聚合由代码处理，不单独建表；相同消息重复导入不产生重复数据；能够按群名、时间、风险类别、风险等级、告警状态和模型版本查询；历史重跑保留新旧版本结果 |
| 10 | 风险告警 | 高风险对话段结束并完成模型判断后，实际项目经理所在企微群在 1 分钟内收到内容完整的告警；中、低风险不即时推送；任务重跑不重复告警；发送失败可查看原因和重试记录 |
